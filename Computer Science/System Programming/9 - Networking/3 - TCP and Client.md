Most internet services use TCP (Transport Control Protocol) because it hides the complexity of the lower-level packet-oriented nature of the internet. TCP is built on top of IPv4 and IPv6 and creates a pipe between two machines that means most of the time, bytes sent over TCP deliver uncorrupted, although high performance code won't even assume that.

TCP gives us a set of virtual sockets that clients can choose to send packets through, and TCP makes sure that applications listening on that port receive them. Only processes with root access can listen on ports less than 1024, and a frequently used port for unencrypted HTTP requests or webpages is port 80. Due to network errors, packets can get dropped and must be retransmitted through TCP without forcing other packets to be dropped. Packets can also be duplicated or sent out-of-order, but TCP fixes all that. It also has a checksum that handles bit errors. The receiver end of a TCP connection has its flow controlled so it doesn't get overwhelmed with packets. Congestion control is performed on the sender side to avoid flooding the network with too many packets. TCP connections also have a lifecycle which starts with the client sending a synchronization packet telling TCP where to start, then the server acknowledges that number, which is again acknowledged by the client. It ends with the client or server sending a FIN packet that forces both of the read and write ends to close.

However, TCP doesn't provide security or encryption. It doesn't verify that an IP address claiming to be a certain website actually is, and anyone can listen in on plain TCP that sends plain text packets. Also, TCP connections have no way to be easily restarted after dying.
# Network Orders

Integers can be represented as either least or most significant byte first, and as long as the machine is consistent, neither is more correct than the other. Networks have their own integer representations which may or may not be the same as the computer's. We can use `htons` and `htonl` to convert `short` and `long` integers from the computer's byte ordering to the network's, and `ntohs` and `ntohl` convert them back. The network order is defined to be big-endian, which means it's the opposite of little-endian x86.
# TCP Client

There are three system calls to connect to a remote machine:

`int getaddrinfo(const char *node, const char *service, constr struct addrinfo *hints, struct addrinfo **res)` takes in a host, port, `hints` filter struct, and a pointer to the output `res` struct. If successful, creates a linked list of `addrinfo` structs at `res`. We can set things like `hints.ai_family` to determine the IP version and `hints.ai_socktype` to determine the protocol (TCP/UDP). On failure, the return value is the error code, which we can parse using `gai_strerror`. We can clean up using `freeaddrinfo(struct addrinfo *ai)`.

`int socket(int domain, int socket_type, int protocol)` creates a network socket and returns a file descriptor for it. The domain is the IP version, the socket type is the network protocol (TCP/UDP). and the protocol is an optional configuration we can leave 0. We can use the result of `getaddressinfo` to fill in these parameters. TCP sockets work similarly to pipes and can be written and read from normally.

`int connect(int sockfd, constr struct sockaddr *addr, socklen_t addrlen)` attempts to connect to the remote machine by passing in the socket's file descriptor and address information stored in the `addrinfo` struct. We also pass in the length because it's nonunique.

This is all we need to create a simple TCP client. However, we can use functions like `setsockopt` which can manipulate socket options. We can also use kernel-provided primitives to mess around with lower protocols.
# Sending Data

We can read or write like any other file descriptor once we have a secure connection. If we're connected to a website, we need to conform to HTTP to get anything that isn't garbage. This means we usually wouldn't use raw TCP to do this or perform operations through sockets. We should always check the return value of `write` and `read` to see how many bytes we actually sent or received. An HTTP request consists of a method (GET, POST, etc.), a resource ("/", "/index.html", etc.), the protocol ("HTTP/1.0"), a newline ("\r\n"), any other parameters, and the request body delimited by two newlines. The server's first response line describes the HTTP version used and whether the request is successful using a three-digit response code (200 for success, 404 for not found, etc).
