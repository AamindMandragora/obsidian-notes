Most filesystems cache significant amounts of disk data in physical memory. In Linux, all unused memory is used as a giant disk cache, which can significantly impact performance as disk i/o is slow, especially for random access requests on spinning disks.

The kernel caches recently used disk blocks for efficiency. However, when we perform a write, we have to decide whether we write to the cache and update memory on eviction or write to the disk immediately, which is safer but slower. Sequential data reads are the most efficient for both spinning and solid-state disks, so operating systems often read ahead, requesting several contiguous disk blocks at a time, reducing the latency.

We can call `sync` to request that a filesystem's changes be flushed to disk, but the operating system can ignore this request. We can use `fsync` to make the same request for a specific file descriptor.

Operating systems can fail in the middle of an operation, which is why modern file systems write down what they're about to do before an expensive operation in a process called **journaling**. Once a fail happens, we can read the journal to see what happened and what files need to be fixed. Disks can fail too, and the mean time to failure can be surprisingly short. If for a single disk the MTTF is 30,000 hours, then the MTTF of a thousand disks is 30 hours, a little over the day. That's also assuming the failures between disks are independent, which isn't usually true.
# Redundant Array of Inexpensive Disks

One way to protect against a disk fail is to store the data twice. A RAID-1 disk array does exactly that, duplicating the writes to a disk onto a backup disk, serving as a copy in case the other disk fails. Having two sources means that reading data is faster but writes can be twice as slow due to the duplication. We can do the opposite as well: RAID-0 splits files between two disks, but if either fails then the files are irrecoverable. This makes writes twice as fast, since we could write some of the file to each disk in parallel. RAID-10 is a combination of the two, where we have two systems of RAID-1 hooked up in RAID-0 to each other. Any one of the four disks can fail and still be recoverable, but we don't count on recovering two disks from opposing partitions.
# Higher Levels of RAID

RAID-3 writes an extra 'parity' bit for every $N$ bits written, where $N$ is the number of original disks, to an additional parity disk. This parity bit is chosen to satisfy an even number of ones in those $N+1$ bits, which means any disk can be computed using the contents of the other disks. However, writing to the parity disk every time makes it a bottleneck and more likely to fail. When two disks are lost, we can no longer rebuild them because we don't have enough information. The probability of that failure is calculated by dividing the mean time to repair a disk by the mean time to one disk's failure over the number of disks minus one. This comes out to around a $1\%$ chance, but it's higher in practice as the i/o-intensive rebuild stresses the disk array. RAID-5 is similar except the parity information is assigned to different disks for different blocks, removing the bottleneck. The one drawback is that the algorithms get a lot more complicated and the number of disks necessary is much higher. Google reports $2$-$10\%$ of disks fail per year, which is incredibly common.
